# ADR 010 — Continuous Integration

**Status:** Implemented (Phase 3).

**Decision:** A GitHub Actions pipeline (`.github/workflows/ci.yml`) runs on every
push and PR with two jobs: **test** and **security**.

**test job:**
- Spins up `postgres:16` + `redis:7` as service containers (health-gated).
- Creates the `shortener_test` DB via a small psycopg2 step (no reliance on a
  preinstalled `psql`).
- Runs the full suite with coverage: `pytest --cov=app --cov-report=term-missing`.
  Current coverage ≈ 88%.

**security job:**
- **Bandit** static analysis over `app/`, **blocking** on medium+ severity — this
  gates *our* code. Currently clean.
- **pip-audit** over `requirements.txt`, **advisory** (`continue-on-error`) — it
  surfaces dependency CVEs without failing an unrelated feature PR on a newly
  disclosed transitive advisory. Findings are reviewed and remediated as fixes
  land (e.g. `python-dotenv` was bumped to 1.2.2; transitive `starlette` CVEs are
  tracked pending a FastAPI bump, since FastAPI 0.115 caps the starlette range).

**Alternatives considered:**
- **Blocking pip-audit** — cleaner in theory, but turns any upstream CVE
  disclosure into a red build on every PR, incentivising `--ignore` noise.
  Advisory + explicit remediation is the pragmatic middle.
- **SQLite in CI** — rejected for the same reason as the tests: `nextval()` is
  Postgres-specific; CI must mirror prod.

**Reason:** This is the concrete artefact behind the "security-first process"
claim — every change is gated on tests against real Postgres+Redis, static
analysis of our code, and a dependency-CVE report.

**Consequences:**
- CI needs the service containers to be healthy before tests (handled via health
  options).
- A separate `requirements-dev.txt` keeps test/scan tooling out of the runtime
  image while giving CI a single install target.
